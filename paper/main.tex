\begin{abstract}
Embodied language-model agents must coordinate interdependent actions while each holds private task information. In dialogue-based coordination, models generate messages and interpret replies to decide what each agent should do, spending inference before the team acts. We propose GenCoord, a decentralized protocol that makes the division of work itself the message. A proposal pairs the sender's skill path with its partner's continuation in Short DSL, a compact language for expressing joint work. Compatible paths form commitments linking the sender's delivery to the partner's work after verified receipt. We check fulfillment separately from original-task success. Complete requests also let a deterministic receiver proceed without another model call. In Minecraft, trained local 0.8B agents match the task success of controlled free-form communication while reducing median commitment time by 68.2\%. The same-field full-key JSON control approaches free-form output length and delay, indicating that the amount generated matters even when messages are structured. With the same prompted DeepSeek model, both protocols complete nearly all tasks, but dialogue generates 2.8 times as many output tokens. Multistep commitments improve held-out-template success from 91.3\% to 98.1\% with fewer decisions. These results point to a design principle for embodied cooperation: make the division of work the message, and spend inference on choosing and revising the work.
\end{abstract}

\section{Introduction}
Language-model-driven embodied agents cooperate by handing over materials, processing objects, and completing actions that depend on a partner's work. We consider teams without a central planner, where each agent holds local observations and private task information that its partner needs to choose compatible work~\cite{white2025collaborating,long2024teamcraft,zhang2024coela}. In dialogue-based coordination, a model generates each message and its partner processes that message before choosing an action. These exchanges consume inference on both sides, so communication can delay the agents' next coordinated action.

We illustrate this information split with two Minecraft agents fulfilling a crafting-table order. Agent $A$ sees the order, whereas $B$ observes which agent the task assigns to craft it. When $B$ is assigned to craft, $A$ should hand over planks; when $A$ is assigned to craft, it should deliver the finished table. The product is the same, but the required actor, transfer object, and continuation differ. Such task rules represent responsibilities that can arise from authorization or resource ownership even when both agents can perform the operation. To coordinate, $A$ needs the consequence of $B$'s private information for their division of work, and $B$ needs a request consistent with the order known to $A$.

Recent embodied systems combine language with planning and execution in several ways. CoELA chooses between communication and environmental actions, RoCo uses dialogue to coordinate robot plans, and MINDcraft supports action-by-action exchanges~\cite{zhang2024coela,mandi2024roco,white2025collaborating}. SMART-LLM constructs team plans through decomposition and allocation, while COHERENT uses a centralized task assigner with feedback from robot executors~\cite{kannan2023smart,liu2025coherent}. Efficiency-oriented approaches reorganize communication~\cite{chen2024scalable,guo2026organized}, reuse plans~\cite{aamas2026_QPUC1624}, or select the observations to share~\cite{aamas2026_WHRE3513}. We instead ask what each message should contain so that decentralized agents spend fewer tokens and calls coordinating their work. That choice matters for frequent decisions and local deployment, where compact models and asynchronous execution are being developed to improve embodied responsiveness~\cite{shukor2025smolvla}.

Our insight is to make the division of work itself the message. A sender proposes the skills it will perform together with the continuation it asks its partner to perform, so the transmitted object already identifies the work on both sides of the handoff. Compatible proposals form a \emph{commitment}, which specifies what each agent owes its partner and when that work becomes due. Because a complete request gives the receiver its continuation, the receiver can check and instantiate that work deterministically. The model's role is then to interpret private information and select or revise the proposed work. We can cut model work in three ways: encode paths compactly, realize complete requests without another model call, and commit beyond the next intermediate decision. A local model can therefore spend its generation budget specifying joint work that its partner can execute directly.

In this paper, we propose \emph{GenCoord}, which implements this idea through \emph{Short DSL}, a compact language for skill paths and partner requests. Each agent generates a proposal from its own information, and the protocol supports both realizing a delivered request and revising a proposal after structured feedback. Our contribution is a peer protocol in which models generate proposals for both agents' physical work and handoff dependencies, while fixed rules resolve and verify commitments. This links decentralized generation to conditional commitment semantics~\cite{singh1998acl,singh2008commitments,chopra2025azorus}, with checks before dispatch and physical readback after execution (Figure~\ref{fig:overview}).

We find that this protocol substantially reduces the model work needed for coordination. Trained local 0.8B agents complete the same tasks through Short DSL, JSON, and controlled free-form communication, yet Short DSL reduces peer traffic by 92.8\% and median commitment time by 68.2\% relative to free-form communication. Our same-field, full-key JSON control produces nearly as many tokens and takes nearly as long as free-form communication. With DeepSeek, both protocols complete nearly all tasks, while dialogue uses 8.1 times the peer traffic and 2.8 times the output tokens; Short DSL reduces mean commitment time by 30.4\%. The local control isolates the encoding of identical fields, and the DeepSeek comparison establishes the cost of each complete communication procedure.

The same protocol also supports longer commitments and different model deployments. Multistep work improves held-out-template success from 91.3\% to 98.1\% and reduces online decisions by 32\%, while structured feedback lets the requester revise the actor and handoff in response to a partner's private information. Local and hosted assignment models can use the same deterministic receiver. Our contributions are:

\begin{itemize}
\item \textbf{A generative coordination protocol.} GenCoord turns local skill paths and partner requests into commitments linking both agents through verified handoffs and feedback.
\item \textbf{Communication as model work.} Controlled comparisons show that compact paths reduce model output, peer traffic, and commitment time, while multistep commitments improve generalization and reduce decisions.
\item \textbf{Independent selection and realization.} One commitment interface supports local and hosted selectors, deterministic reception, and execution of transmitted paths.
\end{itemize}

\section{Related Work}
\paragraph{Embodied LLM agents.}
SayCan combines language-model proposals with skill value functions to select feasible robot actions~\cite{ichter2023saycan}. Voyager builds reusable skills, while Code as Policies and ProgPrompt generate programs using available actions and objects~\cite{wang2023voyager,liang2023code,singh2023progprompt}. MindCraft, MindAgent, and TeamCraft evaluate situated interaction and teamwork~\cite{bara2021mindcraft,gong2024mindagent,long2024teamcraft}, while VillagerAgent and CausalMACE organize task dependencies and Parallelized Planning-Acting overlaps planning and execution~\cite{dong2024villageragent,chai2025causalmace,aamas2026_EXAJ9853}. GenCoord extends model-guided skill selection across agents by making the selected work a message for the partner.

SMART-LLM generates a multi-robot plan through decomposition, coalition formation, and allocation~\cite{kannan2023smart}, while COHERENT couples a central task assigner to executors that report feedback~\cite{liu2025coherent}. Chen et al. compare centralized, decentralized, and hybrid communication~\cite{chen2024scalable}, while Guo et al. organize embodied agents through prompted leadership~\cite{guo2026organized}. GenCoord instead has each agent propose work from its own information and connects the proposals at the handoff. SmolVLA motivates local inference with compact models and responsive execution~\cite{shukor2025smolvla}, while hosted models offer another operating point.

\paragraph{Plans and commitments.}
We build on accounts of shared goals and partial plans in joint intentions, SharedPlans, and STEAM~\cite{cohen1991teamwork,grosz1996collaborative,tambe1997teamwork}, and Contract Net and allocation methods distribute work through contracts and utilities~\cite{smith1980contractnet,gerkey2004mrta,choi2009cbba}. CLIPS infers hidden goals from actions and language, while Li et al. maintain explicit beliefs during collaboration~\cite{aamas2024_p2094,li2023theory}. 

Commitment semantics specifies what agents owe one another and which events activate or discharge those obligations~\cite{singh1998acl,fornara2002operational,singh2008commitments}. Flexible commitment protocols describe how agents enact their commitments~\cite{yolum2002flexible}, while Pippi, Kiko, and Peach address role instantiation, admissible messaging, and communication infrastructure~\cite{aamas2022_p281,aamas2023_p1154,aamas2026_SAXY3841}. Acceptance and counteroffers determine which proposed work enters that commitment~\cite{jennings2001negotiation}.

\paragraph{Communication and computation.}
Learned channels, information bottlenecks, and Optima optimize agent messages~\cite{foerster2016dial,sukhbaatar2016commnet,wang2020imac,chen2024optima}. AutoGen and MetaGPT organize conversations and workflows~\cite{wu2023autogen,hong2024metagpt}, while Gated Coordination, TickingCollab, $\mu$ACP, and AgenticCache address escalation, timing, resource use, and reuse~\cite{jian2026gated,yi2026ticking,aamas2026_PHRW6922,kim2026agenticcache}. MeCo retrieves and reuses plans for similar tasks to avoid invoking the model again~\cite{aamas2026_QPUC1624}. UNCAP selects relevant vehicles and exchanges lightweight messages describing uncertain observations~\cite{aamas2026_WHRE3513}. ReAd learns a sequential advantage function from planned trajectories to guide plan refinement, reducing interaction steps and model queries~\cite{zhang2025read}. GenCoord reduces what agents generate per coordination and directly specifies work that a deterministic receiver can realize. Shared skills connect it to task grammars and ad hoc teamwork~\cite{aamas2024_p544,stone2010adhoc}. We use message interventions inspired by Lowe et al. and Jaques et al. to check request and feedback semantics~\cite{lowe2019pitfalls,jaques2019social}, while the main comparisons measure protocol cost and multistep task performance.

GenCoord makes both agents' executable work the message, connecting their proposed skills through handoff dependencies and fixed commitment checks. Beyond Natural Language compares alternative communication formats, and OPTiMACS learns task-aware message representations for collaborative problem solving~\cite{chen2024beyond,gupta2026optimacs}. In GenCoord, the transmitted content specifies the work that the runtime dispatches, so representation also determines which skills the agents undertake. BSPL, Clouseau, and Azorus address information dependencies, protocol synthesis, and commitment enactment~\cite{singh2011bspl,singh2020clouseau,chopra2025azorus}. We bring those concerns into a protocol whose message content consists of locally generated physical skill paths and whose commitments are checked in the environment. IntentMCTS communicates states that guide partner search~\cite{aamas2025_p481}, whereas GenCoord requests the multistep continuation that its partner will execute. CoELA, RoCo, and MINDcraft coordinate through dialogue~\cite{zhang2024coela,mandi2024roco,white2025collaborating}. GenCoord instead uses the proposed skill paths themselves to establish responsibilities, dispatch skills, and verify fulfillment.

\section{Coordination under Private Information}
\label{sec:information}
We consider two agents $\mathcal A=\{a_i,a_j\}$ that cooperate through environmental actions and messages, with agent $i$ receiving context $x_i=(o_i,h_i,m_i)$ containing its observation, execution history, and received messages. Shared primitives $\mathcal K_0$ define skills, argument types, and grounding rules, while $\mathcal K_i$ adds the task structure available to that agent. We call information in $x_i$ or $\mathcal K_i$ \emph{private} when the partner cannot observe it but needs its consequences to choose compatible work. Because private information can determine the actor, transfer object, destination, or continuation, decentralized decisions depend on what each agent observes and communicates~\cite{bernstein2002decentralized}.

We define a task $z$ by its required outcome and allocation of work, using \emph{binding} $\beta$ for the selected actors, objects, and continuation. The set $\Pi^\star(z;\mathcal K)$ contains the supported paths satisfying that task. In the workcell example, the two processing modes prescribe different crafting actors and handoff objects even though they request the same product. Our tests therefore evaluate the prescribed allocation as well as the terminal world state.

The communication requirement follows directly from the local information available at the decision. When two equiprobable tasks present the same local view but have disjoint acceptable routes, a policy choosing a route from that view has expected success at most $1/2$. We use this paired ambiguity to construct checks of message use, keeping the acceptable task routes distinct from the particular string a model emits. The design question is how to transmit the information so that a partner can act on it, which motivates the executable paths below (Supplement~\S S12).

\section{GenCoord}
\label{sec:method}
GenCoord proceeds from a proposed division of work to a resolved commitment, then checks fulfillment against the execution trace. Its key design choice is to generate the work that each party undertakes in the same representation that the receiver and runtime inspect.

\subsection{From Paths to Commitments}
A grounded task $\tau=(a,k,\mathbf v,\ell,P)$ specifies an actor, skill, typed arguments, location, and predecessors. A proposal $q_i=(s_i,r_{i\rightarrow j})$ pairs the sender's path with a requested continuation for the peer, so both sides of the intended handoff are explicit. We serialize these paths in Short DSL as \texttt{SELF} and \texttt{REQ}, using \texttt{>} for precedence, as in this workcell proposal:
\begin{center}
\begin{minipage}{0.96\columnwidth}
\small\ttfamily
SELF resource.obtain(q=4,item=oak\_planks)\newline
\hspace*{1em}> resource.deliver(q=4,item=oak\_planks,to=agent\_b)\newline
REQ agent\_b craft.item(q=1,input=oak\_planks,\newline
\hspace*{1em}item=crafting\_table)\newline
\hspace*{1em}> resource.deliver(q=1,item=crafting\_table,\newline
\hspace*{2em}dst=order\_chest)
\end{minipage}
\end{center}
When the paths agree on the handoff and their dependencies are acyclic, we merge them into $C_{ij}=(S_i,S_j,\beta,P_C)$, which specifies each agent's work and its ordering. A commitment is created at this resolution step, after the proposed assignment has passed the interaction checks and both sides specify compatible work. The resolver checks compatibility between choices made by the agents. For example, a plank delivery can support a receiver's crafting step only when the actors, item quantity, and dependency agree. This compatibility is established symbolically before dispatch, while the later receipt check establishes that the promised material was actually transferred. Keeping those events distinct allows the same proposal representation to support both generation and deterministic interpretation.

Conditional commitments explain why receipt matters to the receiver's responsibility: the sender's promised delivery establishes the precondition under which the receiver owes its remaining work. Writing $C(d,c,p,q)$ for debtor $d$ owing creditor $c$ outcome $q$ when $p$ holds~\cite{singh2008commitments}, we assign
\begin{equation}\label{eq:commitment}
\operatorname{Obl}(C_{ij})=\{C(a_i,a_j,\top,H_\beta),\ C(a_j,a_i,H_\beta,T_\beta)\}.
\end{equation}
Here $H_\beta$ is verified receipt of the handoff and $T_\beta$ is the declared terminal outcome. Receipt fulfills the sender's obligation and activates the receiver's remaining work, whose completion is checked in the world~\cite{chopra2025azorus}. The receipt remains valid when crafting consumes the transferred materials. In the example, the receiver owes the requested crafting and deposit after it has received the planks, while the sender is responsible for making that transfer. We record the transfer as an event in the trace, so subsequent consumption preserves evidence that the sender fulfilled its delivery.

We distinguish that fulfillment from the original task's success because a commitment can specify the wrong assignment. For a trace $\xi$ ending in world state $\omega_T$,
\begin{equation*}
\begin{aligned}
F(C_{ij},\xi)&=H_\beta(\xi)\land T_\beta(\xi),\\
G_z(\xi)&=\operatorname{ExecOK}(\xi)\land P_z(\omega_T)\land A_z(\xi).
\end{aligned}
\end{equation*}
The predicates $P_z$ and $A_z$ specify the original outcome and allocation, respectively. Thus $F$ evaluates the committed work, whereas $G_z$ evaluates whether that work satisfied the task.

\subsection{Requests and Feedback}
\label{sec:resolution}
In a forward interaction, the receiver produces \mbox{$u_j=R_j(x_j,r^{\mathrm{del}}_{i\rightarrow j},\mathcal K_j)$} from its local context, executable prior, and delivered request, using the inventory expected after the proposed handoff to generate or deterministically instantiate the continuation. The path resolver forms \mbox{$C^{\rightarrow}_{ij}=\operatorname{Resolve}_{\rightarrow}((s_i,r^{\mathrm{del}}_{i\rightarrow j}),u_j)$} when the continuation matches the normalized delivered request, the handoff fields agree, and the merged dependencies are acyclic. Using the delivered request also gives message substitutions a precise operational meaning.

Feedback instead lets the requester revise who performs the work. A deterministic policy reads the requested suffix and the peer's processing mode, returning \textsc{Accept}, \textsc{Reject}, or $\textsc{Counter}(\alpha)$ for an admissible alternative. Acceptance preserves the proposed branch, while a counteroffer changes the allocation and preserves the goal and peer. The requester then generates a revised proposal from its context, initial proposal, and response, after which the feedback resolver checks the resulting handoff and path. Rejection creates no commitment, whereas a counteroffer in our example asks the requester to craft before handing over the finished table. The response therefore communicates the consequence of the peer's mode in the form of a concrete alternative that the requester can incorporate into its own path. The resolver checks the revised paths against the response, including who processes the material and what the requester will deliver. These two interactions place the additional model call on the agent that still has work to determine: the peer realizes the incoming request in the forward route, whereas the original requester revises its proposal in the feedback route. A deterministic peer can perform the former operation when the request already specifies its full continuation.

\subsection{Realization and Execution}
We parse and check the generated message to validate identities, skills, arguments, destinations, and dependencies, after which the materializer constructs the task actions needed for dispatch. The formation backend chooses and expresses the assignment, while the materializer supplies the task details available through the shared graph or received continuation. In the shared-graph configuration it expands an admitted binding through the available task graph. When the sender keeps its graph private, the receiver instead derives this work from the delivered continuation and shared primitives.

After the compiler converts the dispatch plan to Mineflayer skills with navigation and execution parameters~\cite{prismarinejs2026mineflayer}, we execute it and inspect inventories and world objects to verify the transfer and declared outcome (Figure~\ref{fig:grounded}). Because formation, fulfillment, and task success are distinct checks, we can locate whether an unsuccessful trial failed to form a commitment, failed to carry it out, or carried out an inappropriate commitment. Complete paths consequently support deterministic realization without another model call, since the receiver's remaining task is to validate and instantiate the continuation it has already received. For a generated continuation, the same checks determine whether the model followed the request, so the execution interface remains stable across both implementations.

\subsection{Choosing the Implementation}
\emph{Direct Short DSL} (Direct) uses Qwen3.5-0.8B to generate complete paths, while \emph{Factor-Code + Rule} (Factor) predicts a short binding code that a deterministic composer expands into the same object~\cite{qwenteam2026qwen35}. A rule can transfer an explicitly supplied binding, and lexical or embedding retrieval can select one from a description. Hosted generation provides another choice when greater assignment accuracy is valuable, although the service's response time becomes part of the agent's decision latency. Each backend expresses its selected assignment through the same receiver-facing request interface.

Receiver knowledge provides a second design choice. A shared directory maps codes to known continuations, whereas \texttt{PATH} transmits an ordered continuation and \texttt{SLICE} transmits the relevant graph fragment. \texttt{GOAL} instead supplies a target and constraints, which an adapter realizes by searching inventory, container, and block states from the specified handoff. Because this adapter checks the target and constraints, a different legal path can satisfy the same commitment. The sender can transmit a complete path or leave the receiver to recover steps from shared knowledge or search, trading message length against receiver computation (Supplement~\mbox{\S S7--S8}).

\section{Experimental Setup}
\label{sec:setup}
\subsection{Tasks and Inputs}
We evaluate Minecraft cooperation over eight templates in four families: Destination, Recipe, Allocation, and Active Branch (Figure~\ref{fig:families}). Each template pairs two task assignments with balanced frequencies and swaps sender and receiver identities across two role views. For example, Recipe changes what the receiver makes from planks, whereas Allocation changes whether the receiver stores material or uses it for construction. We hold the skill library and task checks fixed across communication methods so their cost can be compared on the same physical work. The workcell diagnostic crosses two goals with two prescribed processing modes, both of whose crafting routes are physically executable. In the controlled local revision diagnostic, a parsed initial proposal must match the prescribed proposal before the second call begins.

We examine task structure by keeping the instance graph private to the sender and transmitting a continuation produced by deterministic projection. These physical tests cover 114 parameter settings within 24 template--motif families, and a distinct probe measures the unchanged Direct model's ability to generate the object. Language tests use 32 original phrasings across 16 assignments or 640 new test descriptions, with 40 per assignment and 256 disjoint calibration descriptions. We evaluate the existing checkpoints on both description sets. The selector chooses between each template's two assignments, after which the same protocol handles the selected work.

\subsection{Models and Protocol Comparisons}
Our local backend is Qwen3.5-0.8B, trained with programmatic examples of local facts and task paths~\cite{qwenteam2026qwen35}. Direct uses 1,920 training examples, two epochs, and 240 updates per seed, with effective batch size 16 and deterministic decoding. We train three checkpoints independently and compare complete training and control procedures for the two horizons, giving single-step control 2,880 examples and 360 updates to supervise its additional intermediate decision. JSON encodes the same fields and uses the same two call stages as Short DSL. Controlled free-form includes dialogue, accumulated context, and structured extraction, with 2,400 training examples and 300 updates. Factor predicts a short assignment code using matched training information.

For the prompted control, we use the same DeepSeek-V4.1-Flash service for both protocols~\cite{deepseek2026api}, with four worked examples balanced across the two role assignments. Dialogue examples use the teacher conversations from the local free-form training, identify both agents' public roles, and begin with the supplier. Within eight calls, the agents exchange natural language and submit structured proposals and acceptances whose explicit control markers the controller recognizes independently of explanatory prose. We test 128 task clusters with two roles and three repetitions per protocol. Feedback tests use 40 paired workcell units, comparing revision from a supplied proposal with the full interaction. Embedding retrieval uses Qwen3-Embedding-0.6B~\cite{qwen3embedding2025}, and the supervised lexical classifier is fitted on the training set. These selectors represent practical choices with different pretraining and supervision (Supplement~\mbox{\S S3--S6}).

\subsection{Measurements and Comparisons}
We measure commitment formation, verified handoff $H$, fulfillment $F$, task success $G$, and the stage where a trial stops, including all assigned trials in task-success rates. Time to commitment (TTC) includes proposal generation and processing up to commitment formation or a stopped attempt, while episode time includes world execution. We measure peer traffic, model calls, input and output tokens, and token-based API charges. For local structured messages, peer payload is the request, whereas free-form payload includes peer dialogue. The private-graph comparison counts application requests and acknowledgments under a common accounting rule.

Local surface and backend comparisons each use a 128-cluster quality pool and a distinct 40-cluster timing sample. Methods run sequentially on one RTX 4090D with hot models and batch size one. The DeepSeek comparison has 768 quality trials per protocol and 64 fresh timing trials per protocol, with the two protocols interleaved in a fixed alternating order, HTTP concurrency one, and one world at a time. Its TTC includes API service and network time. The receiver benchmark measures the receiver stage on a common local device. Selector accuracy is evaluated before world execution on 640 descriptions, while the decision-time comparison uses 128 measurements per strategy.

We report 95\% intervals from 10,000 paired bootstrap draws over task clusters, averaging roles and repeated calls within each unit~\cite{efron1994bootstrap}. For language comparisons, we resample source phrasings within their 16 assignments. Message substitutions preserve the world, local inputs, and call procedure while changing the legal request or response. Their role is to check the protocol, alongside fault injections at admission, handoff, and completion.

\section{Results}
\label{sec:results}
We test how path encoding, commitment length, and receiver implementation affect the model computation needed for coordination. Physical checks distinguish fulfillment from task success.
\subsection{Communication and Model Work}

The full-key JSON control uses the same fields and call stages as Short DSL, yet its output length and delay approach those of controlled free-form communication (Figure~\ref{fig:mechanisms}(a)). Short DSL expresses these fields as skill paths with typed arguments and an explicit precedence separator, reducing peer traffic by 92.8\%, median TTC by 68.2\%, and median episode time by 17.4\% relative to free-form communication. The encoding thus changes the model work needed to express the same task information. GenCoord defines the joint work, handoff dependencies, and commitment checks, while Short DSL makes this object compact to generate.

\subsection{Multistep Work and Feedback}
\label{sec:horizon-results}\label{sec:feedback-results}
Compact encoding reduces the model work spent expressing a plan, while a longer commitment changes how often the agents must decide again. We test this second choice by extending the committed path beyond the next handoff or intermediate decision. On held-out templates, multistep control reaches 98.1\% task success against 91.3\% for single-step control, a paired improvement of 6.9 points $[2.9,10.8]$. Mean online decisions fall from 2.91 to 1.98, a 32\% reduction (Figure~\ref{fig:mechanisms}(c,d)). Multistep control commits past the intermediate stage and uses fewer training examples and updates. The result extends multi-step intent from guiding partner search~\cite{aamas2025_p481} to carrying out a committed sequence, showing that longer commitments improve generalization with fewer decisions.

Feedback lets the requester revise that sequence when its partner has private information about the assignment. Given an initial proposal and correct feedback, DeepSeek completes 419/480 workcell trials (87.3\%); when it generates the initial proposal as well, it completes 414/480 (86.3\%). The revised commitment changes who crafts and which item crosses the handoff, while preserving the requested product. Correct versus alternative feedback has a task-success difference of 87.3 points $[84.4,90.0]$. Alternative feedback changes the workcell's processing assignment: DeepSeek fulfills all 403 formed commitments and delivers the product to its target, while original-task success is zero across 480 trials. A compact response thus revises both agents' work, while fulfillment and original-task checks reveal whether the resulting assignment meets the task.

\subsection{Selection and Receiver Implementation}
\label{sec:binding-results}\label{sec:backend-results}\label{sec:private-structure}\label{sec:request-results}
A complete requested path also makes reception an implementation choice: the receiver can instantiate the work directly instead of generating a continuation. On paired sender outputs, both receivers form the same commitments. Task-success counts differ by two Factor trials and three Direct trials, with all differences arising after formation. Mean calls fall from approximately 1.94--1.95 to one, saving 343 ms $[292,374]$ with Factor and 785 ms with Direct before commitment. Because both implementations subsequently dispatch the work expressed by the request, the comparison separates the model needed to select an assignment from the code needed to realize its specified continuation.

To test the receiver's required knowledge, we keep the sender's instance graph private and supply deterministically projected paths, which complete 456 physical cases. Goal-based search supplies another 100 different legal continuations that also fulfill the commitment and task. GOAL sends fewer first-delivery bytes than PATH, 662 versus 741 including acknowledgment, but uses 2.0 rather than 0.065 ms of receiver computation. The unchanged Direct model forms 43.1\% of complete objects in the corresponding generation probe. The projected-path result establishes the receiver's ability to execute supplied structure, while that probe measures the sender's ability to express it.

The fulfillment and task checks used in the feedback intervention also locate errors in commitments formed from descriptions. In closed-loop runs based on 32 original descriptions, 2,181 of the 2,198 task failures after formation follow fulfillment of an incorrect assignment, while 17 arise during execution.

We therefore examine the deployment tradeoff where a model interprets a task description and selects an assignment (Table~\ref{tab:selection-main}). On 640 new descriptions over the shared task vocabulary, the local Factor model selects correctly in 95.94\% of trials at a mean decision time of 412 ms, compared with 99.97\% at 1,402 ms for DeepSeek. Factor uses about 29\% of the hosted model's measured decision time and makes no API request, whereas DeepSeek supplies the highest assignment accuracy. Routing the lowest-margin retrieval decisions to DeepSeek raises accuracy from 82.19\% to 88.91\%; the same-quota random-upgrade expectation is 84.88\%. The routing point uses the hosted model selectively, while running Factor throughout gives higher accuracy with local computation.

\section{Discussion}
\label{sec:discussion}
\paragraph{Communication spends inference.}
Making joint work explicit reduces inference at several points before the next physical action. Compact paths reduce what agents generate, complete continuations support deterministic reception, and multistep commitments reduce how often the agents decide again. The full-key JSON control varies how task fields are encoded. The other comparisons vary how the receiver processes a received path and how many steps each commitment covers. Together, these comparisons show why a protocol should specify executable work, not only its transmission.

Figure~\ref{fig:mechanisms}(a,b) shows why generated output and elapsed time provide different views of communication cost. Local output length and commitment time change by similar proportions. With the hosted model, however, the timing difference is smaller, which may partly reflect service and network overhead as well as prompt processing. We therefore measure both the work required to produce a commitment and the delay before the agents can use it. Across both deployments, compact paths keep the actors, transfer, and continuation explicit while reducing generation.

\paragraph{Models choose, skills realize.}
Interpreting a description and instantiating a complete continuation are different operations. A language model can select or revise an assignment, while shared skills and a deterministic receiver realize work that the message has already specified. Changing the selector changes assignment accuracy and decision time, while the interface for sending, executing, and checking the selected work stays fixed. The local selector provides a fast, self-contained operating point, and the hosted selector provides higher assignment accuracy. We check the requested work against the commitment and the chosen assignment against the task, distinguishing fulfillment from task success. 

\paragraph{Commitments connect both agents' work.}
The defining object in GenCoord couples the sender's promised delivery to the receiver's work after receipt. This gives decentralized proposals the dependency structure that a centrally constructed joint plan would otherwise provide, while each proposal is generated from the participant's local information. Conditional commitment semantics explains when responsibilities take effect, and physical readback establishes whether the promised actions occurred. Admission, fulfillment, and task checks then serve different engineering purposes: validate the proposed work, detect an incomplete transfer or outcome, and assess whether the selected work satisfies the task. The same trace can consequently guide improvements to the assignment model, the protocol checks, or the physical skill that did not complete its work.

\paragraph{Knowledge, messages, and search.}
A path transmits a selected solution, while a goal and constraints ask the receiver to find one. A shared directory moves recurring task knowledge into the receiver's prior, and Factor's composer expands a short internal prediction into an explicit partner request. These alternatives show why the shortest message and the least computation need not coincide. Designers can choose how much structure to transmit by considering the receiver's knowledge and search cost together with the model work needed to express the message. Each commitment specifies who performs each step, what is handed over, and which outcome the receiver must achieve after receipt.

\paragraph{Limitations.}
We evaluate bilateral assignments in static Minecraft worlds with reliable messaging, shared discrete skills, and paired task alternatives. Extending the protocol to changing environments, larger teams, open-ended task decomposition, and robot platforms with continuous control and perception errors will require corresponding models of revision and responsibility. The static tests leave the cost of revising long commitments after environmental changes unmeasured.

\section{Conclusion}
We introduced GenCoord to let embodied agents communicate their own work and a partner's continuation as commitments. Its compact skill paths reduce communication and model inference costs with a local 0.8B backend, and communicating those paths through the prompted cloud model also reduces generated output and commitment time. Multistep commitments improve task success on held-out templates while reducing decisions, and structured feedback supports changes to the proposed assignment. Because the receiver can instantiate a complete request deterministically, we can choose between local and hosted selectors according to deployment needs while keeping the partner's execution interface unchanged. After the skills execute the committed paths, we check whether the agents fulfilled the commitment and whether their work completed the original task. Making the division of work the message lets models choose and revise that work and lets skills carry it out.

We use the notation in Table~\ref{tab:core-notation} throughout the algorithms, including the distinction between proposed paths and the resolved commitment. Single-step control adds a sender decision after acquisition, whereas the two-call Factor implementation predicts a code at each side and composes the corresponding paths deterministically.

To keep the evaluator's outcome distinct from the state of an individual obligation, we return the following tagged result and report fulfillment alongside original-task success:
\[
\mathcal R=
(\{\mathtt{SUCCESS}\}\times\mathcal C\times\mathcal D)
\;\uplus\;
(\{\mathtt{NO\_COMMITMENT}\}\times\mathcal E)
\;\uplus\;
(\{\mathtt{FAIL}\}\times\mathcal F).
\]
The values $\operatorname{Success}(C,D)$, $\operatorname{NoCommitment}(e)$, and $\operatorname{Fail}(f)$ identify whether a task completes or stops at an earlier stage. Because fulfilling the committed work can still violate the original assignment, a task-failure result may include $H=F=1$ and $G=0$.

\begin{algorithm}[!htbp]
  \caption{Learned Forward Resolution}
  \label{alg:forward}
  \footnotesize
  \begin{algorithmic}[1]
    \Require sender context $x_{\mathrm{snd}}$, receiver context $x_{\mathrm{rcv}}$, prior $\mathcal K$, public episode instantiation $\xi_{\mathrm{pub}}$, executable world $\omega_t$
    \State $\hat y_{\mathrm{snd}} \gets \textsc{Generate}(x_{\mathrm{snd}},\mathcal K,\xi_{\mathrm{pub}})$ \Comment{\artifact{SELF+REQ}}
    \State $q_{\mathrm{snd}} \gets \textsc{Parse}(\hat y_{\mathrm{snd}})$
    \If{$q_{\mathrm{snd}}=\bot$} \State \Return $\textsc{Fail}(\mathtt{PARSE\_FAILURE})$ \EndIf
    \If{$\neg\textsc{ContractCheck}(q_{\mathrm{snd}},x_{\mathrm{snd}},\mathcal K,\xi_{\mathrm{pub}})$}
      \State \Return $\textsc{Fail}(\mathtt{CONTRACT\_REJECT})$
    \EndIf
    \If{$|q_{\mathrm{snd}}.\mathtt{peer\_requests}|\neq1$ \textbf{or} $q_{\mathrm{snd}}.\mathtt{peer\_requests}[0].\mathtt{requested\_plan}=[]$}
      \State \Return $\textsc{Fail}(\mathtt{CONTRACT\_REJECT})$
    \EndIf
    \State $r_{\mathrm{snd}\rightarrow\mathrm{rcv}}\gets q_{\mathrm{snd}}.\mathtt{peer\_requests}[0]$; deliver $r_{\mathrm{snd}\rightarrow\mathrm{rcv}}$
    \State $\hat y_{\mathrm{rcv}} \gets \textsc{Generate}(x_{\mathrm{rcv}},\mathcal K,\xi_{\mathrm{pub}},r_{\mathrm{snd}\rightarrow\mathrm{rcv}})$
    \State $q_{\mathrm{rcv}} \gets \textsc{Parse}(\hat y_{\mathrm{rcv}})$
    \If{$q_{\mathrm{rcv}}=\bot$} \State \Return $\textsc{Fail}(\mathtt{PARSE\_FAILURE})$ \EndIf
    \If{$\neg\textsc{ContractCheck}(q_{\mathrm{rcv}},x_{\mathrm{rcv}},\mathcal K,\xi_{\mathrm{pub}})$ \textbf{or} $q_{\mathrm{rcv}}.\mathtt{self\_plan}=[]$ \textbf{or} $q_{\mathrm{rcv}}.\mathtt{peer\_requests}\neq[]$}
      \State \Return $\textsc{Fail}(\mathtt{CONTRACT\_REJECT})$
    \EndIf
    \State $C \gets \textsc{Resolve}_{\rightarrow}(q_{\mathrm{snd}},q_{\mathrm{rcv}},\mathcal K,\xi_{\mathrm{pub}})$
    \If{$C=\bot$} \State \Return $\textsc{Fail}(\mathtt{RESOLUTION\_CONFLICT})$ \EndIf
    \State $D \gets \textsc{Materialize}(C,\mathcal K,\xi_{\mathrm{pub}})$
    \If{$D=\bot$} \State \Return $\textsc{Fail}(\mathtt{MATERIALIZATION\_FAILURE})$ \EndIf
    \State $\mathtt{status}\gets\textsc{ExecuteAndVerify}(D,\omega_t)$
    \If{$\mathtt{status}\neq\mathtt{SUCCESS}$} \State \Return $\textsc{Fail}(\mathtt{status})$ \EndIf
    \State \Return $\textsc{Success}(C,D)$
  \end{algorithmic}
\end{algorithm}

\begin{algorithm}[!htbp]

  \label{alg:feedback}
  \footnotesize
  \begin{algorithmic}[1]
    \Require requester context $x_{\mathrm{req}}$, peer mode $c_{\mathrm{peer}}$, prior $\mathcal K$, public episode instantiation $\xi_{\mathrm{pub}}$, executable world $\omega_t$, prescribed initial proposal $q_0^\star$

    \If{$\neg\textsc{ContractCheck}(q_0,x_{\mathrm{req}},\mathcal K,\xi_{\mathrm{pub}})$}
      \State \Return $\textsc{Fail}(\mathtt{CONTRACT\_REJECT})$
    \EndIf

      \State \Return $\textsc{Fail}(\mathtt{CONTRACT\_REJECT})$
    \EndIf

    \State $\rho \gets \textsc{ResponsePolicy}(r_{\mathrm{req}\rightarrow\mathrm{peer}},c_{\mathrm{peer}},\mathcal K,\xi_{\mathrm{pub}})$
    \If{$\neg\textsc{ResponseValid}(\rho,r_{\mathrm{req}\rightarrow\mathrm{peer}},\mathcal K,\xi_{\mathrm{pub}})$}
      \State \Return $\textsc{Fail}(\mathtt{CONTRACT\_REJECT})$
    \EndIf

    \EndIf
    \State $\hat y_1 \gets \textsc{Generate}(x_{\mathrm{req}},\mathcal K,\xi_{\mathrm{pub}},q_0,\rho)$ \Comment{ACCEPT or COUNTER}
    \State $q_1 \gets \textsc{Parse}(\hat y_1)$
    \If{$q_1=\bot$} \State \Return $\textsc{Fail}(\mathtt{PARSE\_FAILURE})$ \EndIf
    \If{$\neg\textsc{ContractCheck}(q_1,x_{\mathrm{req}},\mathcal K,\xi_{\mathrm{pub}})$}
      \State \Return $\textsc{Fail}(\mathtt{CONTRACT\_REJECT})$
    \EndIf
    \If{$|q_1.\mathtt{peer\_requests}|\neq1$ \textbf{or} $q_1.\mathtt{peer\_requests}[0].\mathtt{requested\_plan}=[]$}
      \State \Return $\textsc{Fail}(\mathtt{CONTRACT\_REJECT})$
    \EndIf
    \If{$q_1.\mathtt{peer\_requests}[0].\mathtt{target}\neq r_{\mathrm{req}\rightarrow\mathrm{peer}}.\mathtt{target}$}
      \State \Return $\textsc{Fail}(\mathtt{CONTRACT\_REJECT})$
    \EndIf
    \State $C \gets \textsc{Resolve}_{\leftarrow}(q_0,\rho,q_1,\mathcal K,\xi_{\mathrm{pub}})$
    \If{$C=\bot$} \State \Return $\textsc{Fail}(\mathtt{RESOLUTION\_CONFLICT})$ \EndIf
    \State $D \gets \textsc{Materialize}(C,\mathcal K,\xi_{\mathrm{pub}})$
    \If{$D=\bot$} \State \Return $\textsc{Fail}(\mathtt{MATERIALIZATION\_FAILURE})$ \EndIf
    \State $\mathtt{status}\gets\textsc{ExecuteAndVerify}(D,\omega_t)$
    \If{$\mathtt{status}\neq\mathtt{SUCCESS}$} \State \Return $\textsc{Fail}(\mathtt{status})$ \EndIf
    \State \Return $\textsc{Success}(C,D)$
  \end{algorithmic}
\end{algorithm}

The response policy deterministically maps the requested suffix and processing mode to \textsc{Accept}, \textsc{Reject}, or $\textsc{Counter}(\alpha)$, whose alternative is serialized as \artifact{counter\_offer\_id}. Acceptance preserves the proposed branch, while a counteroffer names the admissible change that the requester must incorporate into its revision. Rejection creates no commitment and ends the interaction before a second generation or dispatch. In the controlled workcell diagnostic, exact equality with the prescribed initial proposal gates revision, and the matching proposal joins the delivered response in the next prompt. Table~\ref{tab:response-schema} specifies this contract, while environmental state is accessed by execution and verification rather than by the response policy.

Algorithms~\ref{alg:forward}--\ref{alg:feedback} show how parsing, commitment checks, materialization, and execution compose into a complete interaction. The verifier returns \artifact{SUCCESS}, \artifact{EXECUTION\_FAILURE}, \artifact{HANDOFF\_FAILURE}, or \artifact{TERMINAL\_FAILURE}, so an admitted object can be distinguished from the physical outcome of carrying it out.

\subsection{Resolver Semantics}

The resolved object $C=(S_i,S_j,\beta,P_C)$ contains the operative paths, assignment, and ordering that the materializer needs, while the proposal and response identify how the commitment was reached. The codebook identifier $b$ denotes assignment $\beta$. As in main Eq.~(1), delivery is owed by the sender and completion becomes due after verified receipt~\cite{singh2008commitments,chopra2025azorus}. We evaluate fulfillment as $F(C,\xi)=H_\beta(\xi)\land T_\beta(\xi)$ and task success as $G_z(\xi)=\operatorname{ExecOK}(\xi)\land P_z(\omega_T)\land A_z(\xi)$, keeping the original outcome and allocation predicates fixed when a message changes. A receipt remains valid after its materials are consumed, whereas a rejected proposal creates no physical fulfillment observation.

Before comparing paths, $\operatorname{Actorize}(z,a)$ fills every implicit actor in path $z$ with agent $a$, making the division of work explicit. We then apply $N_{\mathcal K}^{\mathrm{path}}$ or $N_{\mathcal K}^{\mathrm{prop}}$ to normalize aliases, typed defaults, grounded references, assignments, actors, and predecessor semantics.

\paragraph{Forward resolution.}
Define
\[
S_{\mathrm{snd}}=N_{\mathcal K}^{\mathrm{path}}\!\left(\operatorname{Actorize}(q_{\mathrm{snd}}.\mathtt{self\_plan},\mathrm{snd})\right),
\]
\[
R_{\mathrm{rcv}}=N_{\mathcal K}^{\mathrm{path}}\!\left(\operatorname{Actorize}(r_{\mathrm{snd}\rightarrow\mathrm{rcv}}.\mathtt{requested\_plan},\mathrm{rcv})\right),
\quad
U_{\mathrm{rcv}}=N_{\mathcal K}^{\mathrm{path}}\!\left(\operatorname{Actorize}(q_{\mathrm{rcv}}.\mathtt{self\_plan},\mathrm{rcv})\right).
\]
Under the path contract, the receiver realizes the request exactly when
\begin{equation}
\operatorname{Realizes}_{\mathcal K}(U_{\mathrm{rcv}},R_{\mathrm{rcv}})
\iff U_{\mathrm{rcv}}=R_{\mathrm{rcv}}.
\label{eq:realizes}
\end{equation}
This equality compares the ordered tasks and their skills, values, actors, locations, and dependencies after normalization, so accepted aliases and argument ordering may differ. The realized path contains the requested tasks, while the executor adds its deterministic bookkeeping after resolution.

We write $\operatorname{HandoffCompatible}_{\mathcal K,\xi_{\mathrm{pub}}}\allowbreak(S_i,S_j)$ for matching of the producing and receiving actors, item, quantity, locations, and dependency under the public task instantiation. The forward resolver admits $C^{\rightarrow}=(S_{\mathrm{snd}},U_{\mathrm{rcv}},\beta,P_C)$ when the receiver is the request's target, its \artifact{SELF} path is nonempty, its outbound request is empty, Equation~\ref{eq:realizes} holds, and the handoff is compatible. It also requires a complete acyclic merge, preserving each agent's task order and connecting the handoff producer to the receiver's first consuming task. These checks establish an executable commitment, while physical execution establishes receipt. Missing fields, incompatible transfers, multiple selected branches, and cycles return $\bot$.

\paragraph{Feedback resolution.}
Feedback resolution first determines which branch the response permits. Let $\mathcal B_{\mathcal K}$ contain the public branches, let $B$ extract a normalized branch from a legal proposal, and let $\operatorname{AltBranch}_{\mathcal K,\xi_{\mathrm{pub}}}$ map an admissible alternative identifier to its branch. The response selects:
\[
B_{\mathcal K,\xi_{\mathrm{pub}}}^{\mathrm{resp}}(\rho,q_0)=
\begin{cases}
B(q_0), & \rho=\textsc{Accept},\\
\operatorname{AltBranch}_{\mathcal K,\xi_{\mathrm{pub}}}(\alpha), & \rho=\textsc{Counter}(\alpha),\\
\bot, & \rho=\textsc{Reject}.
\end{cases}
\]
After acceptance, the requester may change surface expression while preserving the initial proposal's normalized branch, peer, and goal. After $\textsc{Counter}(\alpha)$, it preserves the peer and goal but replaces the operative branch with the named alternative. Rejection ends processing without creating a commitment.

For accepted and countered proposals, define
\[
S_{\mathrm{req}}=N_{\mathcal K}^{\mathrm{path}}\!\left(\operatorname{Actorize}(q_1.\mathtt{self\_plan},\mathrm{req})\right),
\]
\[
R_{\mathrm{peer}}=N_{\mathcal K}^{\mathrm{path}}\!\left(\operatorname{Actorize}(q_1.\mathtt{peer\_requests}[0].\mathtt{requested\_plan},\mathrm{peer})\right).
\]
$\textsc{Resolve}_{\leftarrow}$ requires
\[
B(q_1)=B_{\mathcal K,\xi_{\mathrm{pub}}}^{\mathrm{resp}}(\rho,q_0),
\]
$\operatorname{HandoffCompatible}_{\mathcal K,\xi_{\mathrm{pub}}}(S_{\mathrm{req}},R_{\mathrm{peer}})$, and a complete acyclic merge $P_C$, returning $C^{\leftarrow}=(S_{\mathrm{req}},R_{\mathrm{peer}},\beta,P_C)$ when those conditions hold.
The materializer uses the resolved paths to construct $D=\textsc{Materialize}(C,\mathcal K,\xi_{\mathrm{pub}})$, instantiating task actions, actors, locations, dependencies, and their attached checks. Because these are task-level operations, materialization precedes compilation into navigation, inventory transfers, and other Mineflayer execution parameters.

\subsection{Short DSL Grammar}

\begin{lstlisting}[style=gcpdsl]
program   ::= self_line NEWLINE req_line
self_line ::= "SELF -" | "SELF " path
req_line  ::= "REQ -" | "REQ " agent " " path
path      ::= task (" > " task){0,4}
task      ::= skill "(" [args] ")"
args      ::= arg ("," arg)*
arg       ::= key "=" value
key       ::= ident
value     ::= json_string | json_number
            | "true" | "false" | "null" | atom
skill     ::= control.wait | resource.obtain
            | resource.deliver | craft.item
            | transform.supply_input
            | transform.supply_fuel
            | transform.collect_output
            | build.component
ident     ::= [A-Za-z][A-Za-z0-9_]*
agent     ::= atom
atom      ::= [A-Za-z0-9_.:/+-]+
json_number ::= JSON numeric literal
json_string ::= RFC 8259 double-quoted string
\end{lstlisting}

We define a canonical grammar while allowing compatible spellings to normalize to the same task object, because the contract concerns the specified work rather than argument order. Values are recognized as quoted JSON strings, complete JSON numbers, reserved literals, and then unquoted ASCII atoms, with escapes decoded before type checking. Quoted strings are scanned atomically, including embedded punctuation and escaped quotes. The serializer uses \artifact{q}, \artifact{item}, \artifact{input}, \artifact{to}, \artifact{dst}, \artifact{bind}, \artifact{site}, \artifact{from}, \artifact{dst\_role}, \artifact{loc}, and \artifact{station}. The parser also canonicalizes the aliases \artifact{count}/\artifact{quantity}, \artifact{target\_agent\_ref}/\artifact{to\_agent\_id}, \artifact{destination}, \artifact{destination\_role}, \artifact{from\_agent\_id}, \artifact{location\_ref}, and \artifact{binding\_id}. Contract checks validate fields and types after parsing, rejecting duplicate keys, unsupported paths, invalid atoms, trailing text, and empty requested continuations.

Each nonempty path contains one to five tasks with positive integer quantities, grounded location references, and an optional public branch identifier. The fields \artifact{to} and \artifact{bind} name the peer and branch, while \artifact{dst}, \artifact{site}, \artifact{loc}, and \artifact{station} supply grounding references. The separator \artifact{>} proposes precedence for resolution, and \artifact{REQ -} produces an empty \artifact{peer\_requests} list. Parsing returns $\bot$ for malformed text, whereas a parsed object can subsequently receive \artifact{CONTRACT\_REJECT}.

We distinguish a syntactically admissible string from an object that satisfies the task contract, since the two checks answer different questions. Let $\mathcal Y_{\mathrm{parse}}$ contain admissible strings, $\mathcal Q_{\mathrm{parsed}}$ parsed proposals, and $\mathcal Q_{\mathrm{legal}}(\mathcal K,\xi_{\mathrm{pub}})$ proposals passing the typed contract. Parsing maps into $\mathcal Q_{\mathrm{parsed}}\cup\{\bot\}$, giving
\[
\mathcal Y_{\mathrm{legal}}(\mathcal K,\xi_{\mathrm{pub}})
=\{y\in\mathcal Y_{\mathrm{parse}}:\operatorname{Parse}(y)\neq\bot,\;
\operatorname{ContractCheck}_{\mathcal K,\xi_{\mathrm{pub}}}(\operatorname{Parse}(y))=\mathtt{true}\}.
\]
For a legal string, decoding applies proposal normalization after parsing: $\operatorname{Decode}_{\mathcal K,\xi_{\mathrm{pub}}}(y)=N_{\mathcal K}^{\mathrm{prop}}(\operatorname{Parse}(y))$. We encode legal objects as canonical strings in $\mathcal Y_{\mathrm{canon}}(\mathcal K)$, defining equivalence between two legal strings by
\begin{equation}
y_1\equiv_{\mathrm{sem}}y_2
\iff
\operatorname{Decode}_{\mathcal K,\xi_{\mathrm{pub}}}(y_1)
=
\operatorname{Decode}_{\mathcal K,\xi_{\mathrm{pub}}}(y_2).
\end{equation}
We check the following round-trip invariant for every legal proposal $Q$, which states that encoding and decoding preserve its normalized task meaning:
\begin{equation}
\operatorname{Decode}_{\mathcal K,\xi_{\mathrm{pub}}}(\operatorname{Encode}_{\mathcal K}(Q))
=
N_{\mathcal K}^{\mathrm{prop}}(Q).
\end{equation}
The invariant preserves the complete ordered paths, target peer, typed arguments, actors, grounding references, and dependencies, allowing serialization to change without changing the work resolved by the protocol.

\paragraph{Workcell Revision Gate.}
In the controlled workcell diagnostic, we invoke revision when the parsed initial proposal exactly matches the prescribed object, which then enters the history as \texttt{INITIAL\_PROPOSAL\_DELIVERED}. \paragraph{Delivered content and evaluation references.}
Forward evaluation preserves the original proposal, delivered request, receiver output, and admitted object because they serve different purposes. Request consistency can reject a syntactically legal alternative that contradicts the delivered request, as the examples in Section~\ref{sec:supp-api} illustrate. \paragraph{Workcell task predicates.}

We compare the admitted assignment with the original task and verify its physical consequences, using a shared candidate graph in the core tests. In the private-structure tests, the message supplies the continuation that the receiver combines with its shared primitives.

\section{Prompted Communication and Revision}
\label{sec:supp-prompted}
This section supports main Sections 6.1--6.2 by comparing the two communication protocols with the same DeepSeek model and by evaluating revision after a partner supplies structured feedback. We describe the dialogue contract before reporting quality, model usage, and the independent timing sample, so the comparison can be interpreted as two ways to form the same kind of commitment.

\subsection{Messages, Examples, and Acceptance}
Both protocols use DeepSeek-V4.1-Flash for the two participants, the same task instances, and the same skill vocabulary, commitment checks, and world executor. Each prompt contains four worked examples, two for each role orientation, clearly separated from the current instance. The dialogue examples are the teacher conversations used to train the local controlled free-form system. All are initiated by the material supplier, and the current prompt identifies the agent's and partner's public roles. Short DSL likewise uses role-balanced examples with instructions appropriate to the agent's current role. The demonstrations and serialized task context enter the input-token counts alongside the interaction history. These prompt components are specific to each protocol, so input totals include both the examples that teach the protocol and the messages exchanged while solving the task.

The dialogue protocol allows natural-language discussion accompanied by structured control markers, with at most eight logical model calls. A \artifact{COMMIT} marker encloses the two agents and their proposed task lists, while a valid \artifact{ACCEPT\_COMMIT} accepts a referenced proposal. The partner can also close the commitment by submitting the matching valid object. The controller validates the structured object and acceptance relationship. Explanatory text can discuss conditions or alternatives without changing a valid control marker, whereas an explicit \artifact{<REJECT/>} rejects the proposal. Thus the two agents may explain their work in natural language while the markers identify precisely what they submit and accept.

For example, a supplier can state which branch the order requires, promise to obtain and deliver its material, and include the corresponding structured proposal in the same turn. The receiver then accepts the proposal or submits the matching object before the controller closes the commitment. The complete example dialogues in the supplementary data show both forms of acceptance. Short DSL instead expresses the sender's work and requested continuation directly as skill paths, which the path resolver checks under the protocol in Section~\ref{sec:supp-lifecycle}.

\section{Selection before Commitment}
\label{sec:supp-prospective-selection}

This section supports the assignment choices in main Section 6.3 by testing fixed selectors on new descriptions and measuring selective use of additional generation. We report the complete prospective comparison with Factor, followed by assignment accuracy and decision costs when DeepSeek supplies the hosted alternative.

\subsection{Descriptions and Prospective Design}
We generate descriptions with a language model from task specifications and screen them for a unique intended assignment. The corpus contains 928 descriptions: 32 for execution checks, 256 for calibration, and 640 for testing. Each of 16 choices has 16 calibration descriptions and 40 test descriptions, with the split fixed before scoring.

We keep the same three Factor checkpoints, Qwen3-Embedding-0.6B retriever, and 64-description training index, while expressing the tasks through newly written descriptions. For example, a description may require a crafting table while explicitly mentioning that a chest would be unsuitable. This changes the wording of a familiar choice without retraining either selector.

We calibrate on the difference between retrieval scores for the two legal assignments, selecting the 52nd smallest margin among 256 calibration descriptions. The resulting threshold, approximately $0.00942109$, uses strict inequality, so the tied threshold value stays with retrieval. It routes 97/640 test descriptions to additional generation, or 15.2\%, with the threshold fixed before their scores are evaluated.

\subsection{Strategies and Physical Outcomes}
Retrieval selects an assignment and composes its request, whereas Factor predicts the assignment code before the same deterministic composition. Selective upgrading first runs retrieval and invokes Factor when the score margin falls below the threshold. \subsection{Paired Local Information}
\label{sec:supp-ambiguity}
The local-information bound supports the diagnostic construction described in main Section 3. Consider equiprobable tasks $z_1,z_2$ with the same local view and disjoint acceptable route sets $\mathcal P_1,\mathcal P_2$. A policy choosing a route from that view has a common route distribution $\mu$, and therefore
\[
\frac{\mu(\mathcal P_1)+\mu(\mathcal P_2)}{2}\leq\frac12.
\]
The inequality follows because probabilities assigned to disjoint sets sum to at most one. We use the bound to construct a balanced check of whether a delivered request or response supplies the information needed for the prescribed route.

To quantify message substitution, let $Y_z(m)$ denote task success after message $m$ is delivered in task $z$, and let $\overline Y_z$ average its repeated role and model evaluations. We replace the true message $m_z$ with a legal alternative $\widetilde m_z$ under the same world and call procedure, defining
\begin{equation}\label{eq:supp-content-effect}
\widehat\Delta_{\mathrm{content}}=\frac{100}{|\mathcal Z|}\sum_{z\in\mathcal Z}\big[\overline Y_z(m_z)-\overline Y_z(\widetilde m_z)\big].
\end{equation}
Both outcomes use the original task specification, so the difference measures the consequence of the delivered content while fulfillment is evaluated against the commitment actually formed.

\begin{samepage}
For architecture accounting, let $\mathcal A_t\subseteq\mathcal A$ be the participating agents at round $t$, let $E_t\subseteq\mathcal A\times\mathcal A$ be the directed active-edge set, and let $\mathcal M_{ij}^t$ be the complete sequence of application messages sent on directed edge $(i,j)$. The function $b(m)$ counts canonical UTF-8 payload bytes, including any application wrapper present in $m$ but excluding transport framing. Let $m_{i,\uparrow}^{t}$ and $m_{i,\downarrow}^{t}$ denote centralized upload and download payloads. With $R_c$ centralized rounds and $R_l$ local rounds,
\begin{align}
B_{\mathrm{central}}
  &= \sum_{t=1}^{R_c}\sum_{i\in\mathcal A_t}
     \left[b(m_{i,\uparrow}^{t})+b(m_{i,\downarrow}^{t})\right], \\
B_{\mathrm{local}}
  &= \sum_{t=1}^{R_l}\sum_{(i,j)\in E_t}
     \sum_{m\in\mathcal M_{ij}^{t}} b(m).
\end{align}
Feedback sent in the reverse direction belongs to the corresponding edge $(j,i)$. Totals depend on coordination rounds; peer traffic also depends on active edges and messages per edge.
\end{samepage}

\paragraph{Two legal branches that violate the request.}
In the Deposit-or-Build example, the receiver is asked to construct an object but generates a deposit instead. The displayed request and output are the transmitted and generated strings from the first API repetition, with Agent B sending to Agent A:
\begin{lstlisting}[style=gcpdsl]
Delivered:
REQ agent_a build.component(bind=BUILD,q=1,item=cobblestone,site=marker_site)
Generated:
SELF resource.deliver(bind=DEPOSIT,q=4,dst=reserve_chest,item=cobblestone)
REQ -
\end{lstlisting}
\Needspace{9\baselineskip}
The Remaining Terminal example has the same sender and receiver roles, but substitutes a depot continuation for the requested marker construction:
\begin{lstlisting}[style=gcpdsl]
Delivered:
REQ agent_a build.component(bind=MARKER_TERMINAL,q=1,item=oak_planks,site=terminal_marker)
Generated:
SELF resource.deliver(bind=DEPOT_TERMINAL,q=2,dst=terminal_chest,item=oak_planks)
REQ -
\end{lstlisting}
Although both outputs have valid syntax and name a public branch, request checking rejects them because their work contradicts the delivered request. The examples therefore illustrate a consistency requirement applied before world execution.

\paragraph{Information absence and grounded outcomes.}
Without a request, DeepSeek forms 795 commitments and selects the correct assignment in 385 of them, or 48.4\% of formed cases. Its all-assigned success is 40.1\% because another 165 trials stop during formation, consistent with an information upper bound that permits lower success. Across both backends and conditions, all 2,807 formed plans selecting the wrong goal fail the task, whereas all 4,684 matching plans succeed. This verifies the link from the admitted branch to the mutually exclusive terminal target.

\subsubsection{Model, Prompt, and Generation Settings}

The request-transfer diagnostic called DeepSeek-V4.1-Flash through the service alias \texttt{deepseek-flash} on 2026-09-28, using the prompt and settings below. The API documentation citation records its consultation date of September 29~\cite{deepseek2026api}, distinct from the experiment's access date.

We used an Anthropic-compatible endpoint with \texttt{thinking.type} set to \texttt{disabled} and an 8,192-token output limit. The request also set \texttt{output\_config.effort} to \texttt{high}, while temperature, top-$p$, seed, tools, and stop sequences were omitted. Each call supplied one user message and the diagnostic allowed four concurrent calls. Parsing removed an optional outer Markdown fence before applying the task contract, and unsuccessful generations remained in the assigned outcomes.

Each prompt provides four training examples, one from Active Order Branch, Build Site A/B, Chest/Crafting Table, and Deposit/Build. Sender and receiver calls use the examples for their own stage, beginning with the following instruction:
\begin{lstlisting}[style=gcpdsl]
Four TRAIN syntax examples; solve only the final MODEL_INPUT.
\end{lstlisting}
After the examples, the prompt appends \texttt{CURRENT INSTANCE} and the agent's local input, followed by the task instruction:
\begin{lstlisting}[style=gcpdsl]
Use only MODEL_INPUT. Generate self tasks and, when locally justified, one peer request. Return exactly two Short DSL lines: SELF ... and REQ .... No prose or semantic repair.
\end{lstlisting}
The local input identifies the agent and includes its task structure, observations, history, and delivered messages, while the sender's private choice appears only in the sender view. The accompanying data contain the complete examples and prompts. Local calls use their checkpoint prompts with deterministic decoding and a 128-token output cap, so the common interface is evaluated with each backend's stated generation settings.

\subsubsection{API Timing and Generation Settings}

\paragraph{API deployment timing.}
We also time the two-call API protocol on 64 role instances repeated three times, with sequential calls and no model warm-up. Among 192 trials, 189 form commitments with median TTC 1.52 s, mean 2.45 s, 95th percentile 2.70 s, and maximum 154.24 s. These measurements include the service, network, and retry time of the evaluated API interaction.

The diagnostic uses non-thinking generation with an 8,192-token cap, allowing the complete structured response to be returned under the prompt specified above.
